Shopware · Entity-Abhängigkeiten · Quelle: Entity-Schema ()

In welcher Reihenfolge lassen sich Shopware-Daten laden?

Abgeleitet aus allen Entities der Instanz, inklusive B2B, Custom Products, CMS-Extensions und Digital Sales Rooms. Die Pakete sind so geschnitten, dass jede Pflicht-Referenz auf ein Paket zeigt, das vorher geladen wird. Klick ein Paket an: Hellblau braucht das Paket direkt, Dunkelblau indirekt (weil ein Vorgänger es braucht). Orange und Lila sind nur optional bzw. weich verknüpft, Grau braucht das gewählte Paket.

Pflicht-FK: ohne Ziel schlägt der Import fehl optionaler FK: geht auch leer, lässt sich später per PATCH setzen weich: ID steckt in JSON, Shopware prüft sie nicht, sie bricht nur still
Wofür das gilt: Shopware mit allem, was Shopware selbst mitbringt (Kern, Commercial, eigene Plugins), ohne Fremd-Plugins. Als Referenz für die meisten 6.7-Projekte geeignet. Details
  • Weniger Umfang ist unkritisch. Fehlen einem Projekt Lizenz-Features oder Plugins, fallen nur Entities weg. Dadurch entsteht keine neue Abhängigkeit, die Reihenfolge bleibt gültig.
  • Fremd-Plugins und Apps bringen eigene Tabellen mit. Die tauchen hier nicht auf, und ihre IDs in JSON-Feldern fehlen in Sonderfall 3. Dann das Schema der Kundeninstanz ziehen und die Seite neu bauen.
  • Versionen: Stand ist . Minor-Updates ergänzen gelegentlich Felder oder Tabellen, nach einem Major-Update (z. B. 6.8) neu bauen.
  • Was abgeleitet und was entschieden ist: Felder, Fremdschlüssel und Pflicht-Kennzeichen stammen aus dem Schema. Paketgrenzen und die Liste der JSON-Verweise sind ein Vorschlag, keine offizielle Shopware-Einteilung. Garantiert ist, dass keine Pflicht-Referenz auf ein späteres Paket zeigt.
Schritt 0: Plugins und Apps installieren. Sie bringen Entities (z. B. swag_cms_extensions_*) und CMS-Block-Typen mit. Ohne Code gibt es die Tabellen gar nicht.

    Sonderfälle beim Import

    Wo die Reihenfolge allein nicht reicht

    Der Ladeplan sortiert alle Pflicht-Verweise so, dass ihr Ziel schon existiert. Drei Arten von Verweisen lassen sich darüber nicht auflösen. Sie brauchen beim Import einen eigenen Handgriff. Im Ladeplan stehen sie pro Paket zusätzlich unter „Besonderheiten in diesem Paket“.

    1 · Gegenseitige Pflicht-Verweise

    Was passiert: Zwei Tabellen verlangen jeweils die andere. Ein Kunde braucht seine Standardadresse (customer.defaultBillingAddressId), die Adresse braucht ihren Kunden (customer_address.customerId). Egal welche zuerst kommt, der Import schlägt fehl.

    So gehst du vor: Beide in einem Schreibvorgang anlegen: den Kunden mit seinen Adressen als verschachtelte Payload, oder beide in derselben Sync-Operation. Innerhalb eines Requests löst Shopware die Reihenfolge selbst.

    Betrifft diese Paare:

      2 · Verweise auf spätere Pakete

      Was passiert: Ein optionales Feld zeigt auf ein Paket, das laut Plan erst später kommt. Ein Angebot kennt zum Beispiel die Bestellung, die daraus entstanden ist (quote.orderId), aber Bestellungen werden nach der B2B Suite geladen. In der Matrix sind das die orangen Zellen rechts oberhalb der Diagonale.

      So gehst du vor: Beim ersten Durchlauf das Feld leer lassen. Wenn das Zielpaket geladen ist, setzt ein zweiter Durchlauf die Verweise per PATCH.

      Betrifft diese Felder:

        3 · IDs in JSON-Feldern

        Was passiert: Manche Verweise stecken als ID in einem JSON-Feld, etwa die Produkte eines CMS-Sliders oder die Kategorien einer Regelbedingung. Shopware prüft sie beim Schreiben nicht. Fehlt das Ziel, gibt es keinen Fehler, sondern einen leeren Slider oder eine Regel, die nie greift.

        So gehst du vor: Die UUIDs aus dem Quellsystem übernehmen, dann stimmen die Verweise automatisch, sobald das Ziel geladen ist. Nach dem Import stichprobenartig prüfen. Diese Liste ist von Hand gepflegt und nicht vollständig, Plugins können eigene JSON-Felder mitbringen.

        Bekannte Felder:

          Erzeugt aus /api/_info/entity-schema.json (Shopware , Shop ). Ausgewertet: many-to-one und besitzende one-to-one Beziehungen. Weggelassen: Versionierung, createdById/updatedById. Weiche JSON-Verweise sind von Hand ergänzt und nicht vollständig.
